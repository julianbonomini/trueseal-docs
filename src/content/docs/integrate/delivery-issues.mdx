# Delivery issues

Your user's old laptop runs last year's version of your app, and their phone runs this week's. The phone sends a note the laptop can't read yet. Nothing has gone wrong in a way your app could fix, but the user should hear that the laptop needs an update. That is what the delivery-issue stream is for.

## The delivery-issue stream

`onDeliveryIssue(listener)` registers a listener for every message the library couldn't deliver or handle, on this device or on its way out of it. It returns a handle that cancels the listener. Listening is optional, and ignoring the stream is safe.

Issues stay on the device and are never sent to another device or to the relay. The relay can still tell that this device runs an older protocol version, from the messages it leaves unacknowledged.

## Incoming messages

| Issue | What happened | What your app should do |
|---|---|---|
| `unreadable(malformed)` | A message couldn't be decoded or authenticated. The library acknowledged and dropped it. | Nothing. Log it if you collect diagnostics. |
| `unreadable(senderOutdated)` | Another device sent a message in an older protocol version than this device supports. It was dropped. | Tell the user one of their devices needs an update. |
| `unreadable(expired)` | The message was sent more than 60 days ago{/* TODO: Shared Fact replayWindow */}, so it is outside the Replay Window. It was dropped. | Nothing. The data is lost on this device. If it matters, your app can ask another device to send its current state again. |
| `unreadable(droppedWhileHeld)` | More than about 100 newer-version messages{/* TODO: Shared Fact heldBlobCap */} were waiting for this device, and the oldest one was dropped to make room. | Ask the user to update the app now. Messages are already being lost. |
| `unauthorized` | The message failed the pairing or membership rules, for example its sender isn't a member. It was dropped. | Nothing. Log it if you collect diagnostics. |
| `heldForUpgrade(version)` | A message in a newer protocol version is waiting on the relay, unacknowledged, until this device upgrades. | Tell the user to update the app. After the upgrade the message is handled, out of order with the messages around it. |
| `handlerGaveUp(messageId, error)` | Your handler threw on all 5 attempts{/* TODO: Shared Fact handlerAttempts */}. The message was acknowledged and dropped. | Treat it as a bug in your handler and report `error`. If the data matters, ask the sending device to send it again. |

`heldForUpgrade` is the first exception to the delivery promise. A held message reaches your handler after messages that were sent later. `unreadable(droppedWhileHeld)` is what happens if the device doesn't upgrade in time.

## Outgoing messages

The relay answers a refused push with a typed code that carries no content. A temporary refusal (the recipient's inbox is full, the relay is limiting the rate, or the relay is unavailable or hit an internal error) keeps the message in the outbox, and the library retries it with backoff. A permanent refusal removes it.

| Issue | What happened | What your app should do |
|---|---|---|
| `sendFailed(messageId, tooLarge)` | The relay refused the message for good, because it is over the relay's own size limit. An Operator may set that limit lower than the Protocol Size Limit. | Tell the user the message wasn't delivered. Send smaller messages, or pass the relay's limit as `maxPayloadBytes` to `open()` so `send()` refuses them up front. |
| `sendFailed(messageId, malformed)` | The relay refused the message for good, because it couldn't parse it. | Treat it as a bug and report it. |
| `sendFailed(messageId, expired)` | The message was still in the outbox 30 days{/* TODO: Shared Fact outboxExpiry */} after `send()`, for example because the device was offline all that time. It was removed. | Tell the user it wasn't delivered, and send it again if it still matters. |

`sendFailed` is the second exception to the delivery promise. The recipient never gets that message, and the messages sent after it still arrive, so the recipient sees a gap.

When the relay speaks a Transport Version this library doesn't support, `connection` becomes `relayVersionUnsupported{min, max}` and no `sendFailed` is raised. Messages stay in the outbox until your app ships a library that speaks the relay's version.

## Errors from `send()`

These are thrown by the call, before anything enters the outbox, so they never appear on the delivery-issue stream.

| Error | What happened | What your app should do |
|---|---|---|
| `payloadTooLarge{max}` | The body is over `max`, the Protocol Size Limit of 61,440 bytes{/* TODO: Shared Fact protocolSizeLimit */} or the lower `maxPayloadBytes` your app passed to `open()`. | Split the data or send a reference to it. |
| `notMember{status}` | `status` isn't `member`. | Wait until the device has joined, or hide the send action while it hasn't. |
| `closed` | The app called `close()` on this `TrueSeal` object. | Open a new one. |

## What isn't reported

- A message that waits on the relay longer than its TTL, 30 days by default{/* TODO: Shared Fact relayTtlDefault */}, is deleted by the relay. The sender saw the relay accept it, and the recipient never sees it, so neither device gets an issue. See [Inbox and TTL](/docs/operate/inbox-and-ttl).
- A duplicate is dropped without an issue.
- Messages a device hadn't sent when it was removed, or when its group was destroyed, are dropped without an issue. See [Membership](/docs/integrate/membership) and [Destroy Group](/docs/integrate/destroy-group).

## What stays your app's job

- Deciding which issues the user should see. Most apps show `heldForUpgrade` and `unreadable(senderOutdated)` as an update prompt, show `sendFailed` as an undelivered message, and log the rest.
- Fixing the handler when `handlerGaveUp` appears.
- Asking for data again when a message was lost and it matters to your app.
