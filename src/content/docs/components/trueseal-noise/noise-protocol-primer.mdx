# Noise Protocol Primer

The Noise Protocol Framework is a spec for building secure channel protocols. WireGuard is built on it. Signal uses it. trueseal-noise wraps [snow](https://github.com/mcginty/snow), a Rust implementation.

This page is a from-scratch walkthrough. No prior crypto-protocol knowledge assumed.

## Why not TLS?

TLS is the default answer for encrypted transport, and it works. The problem is the baggage that comes with it:

- A certificate authority hierarchy. Trust roots in a set of organisations that sign certificates on behalf of domain names. Great for the web. Meaningless for two devices talking to each other.
- A complex negotiation phase. TLS 1.3 is much cleaner than what came before, but it still supports dozens of cipher-suite combinations and extension mechanisms.
- Identity is tied to domain names, not keys.

Noise goes the other way. No certificate authorities. Identity is a keypair you generate yourself. The cipher suite is fixed — no negotiation, no downgrade attacks. The whole spec is about 50 pages and you can sit down and read it.

For a system where identity is a keypair and trust is established out-of-band (pairing), Noise is a much better fit than TLS.

## The core idea: chained DH

A Noise handshake is a sequence of Diffie-Hellman operations interleaved with message exchanges. Each DH mixes new key material into a running shared secret. By the end of the handshake, both peers have derived the same shared secret — without ever sending it — and that secret keys the encrypted channel.

A quick recap of Diffie-Hellman: if Alice has keypair `(a_priv, a_pub)` and Bob has `(b_priv, b_pub)`, then:

```
DH(a_priv, b_pub) == DH(b_priv, a_pub)
```

Both sides compute the same value using their own private key and the other side's public key. An observer who sees both public keys can't compute it. The private keys are required.

In Noise, several DH operations are chained together using HKDF (a key derivation function). Each DH output gets mixed into the current chaining key, producing a new one. By the end, the chaining key is a function of *every* DH operation that took place — so both peers must have contributed the right keys at every step, or the derived keys don't match and nothing decrypts.

## Three internal objects

The Noise spec defines three pieces that cooperate during a handshake:

**CipherState** — wraps a symmetric encryption key and a nonce counter. Encrypts and decrypts using ChaCha20-Poly1305. The nonce increments on every operation, so encrypting the same plaintext twice still produces different ciphertext. If the nonce ever overflows, the implementation panics. Quietly continuing with a broken nonce would be a disaster, so the correct behaviour is to crash loudly.

**SymmetricState** — keeps two values around: a chaining key (`ck`) and a handshake hash (`h`). Every DH output is mixed into `ck` via HKDF, producing a new `ck` and a fresh `CipherState`. Every message sent or received is mixed into `h` via BLAKE2s. By the end of the handshake, `h` is a hash of every byte exchanged — a transcript both sides must agree on. That's what binds the handshake messages together and stops anyone from substituting or reordering them.

**HandshakeState** — orchestrates the whole thing. Holds the local static keypair, the local ephemeral keypair, and any remote public keys as they're revealed. Drives `SymmetricState` through the correct sequence of DH operations and message reads/writes for the chosen pattern.

## Static and ephemeral keys

Each peer uses two kinds of keypairs during a handshake:

**Static keypair** — long-term identity. Generated once and reused across every session. For trueseal, this is the device's noise keypair, kept in local Session State.

**Ephemeral keypair** — generated fresh for each handshake and thrown away afterwards. The ephemeral keys are where forward secrecy comes from: even if the static private key gets compromised later, past session keys can't be reconstructed because the ephemerals are gone.

## Forward secrecy

Forward secrecy means compromising a long-term key today doesn't decrypt traffic from the past.

In Noise, session keys are derived from a mix of static and ephemeral DH operations. The ephemeral keys are per-handshake and discarded. Someone who steals a static private key can impersonate that device in *future* sessions — but they can't recompute session keys from *past* sessions, because those depended on ephemeral keys that no longer exist anywhere.

## The handshake hash

When a Noise handshake completes, both sides produce a `handshake_hash`: a BLAKE2s digest of the entire transcript. Both sides must arrive at the same value. This is what makes the handshake tamper-evident — if any message was modified, reordered, or injected, the hashes don't match and decryption of the first post-handshake message fails.

The handshake hash is also used as associated data for post-handshake encryption. It's mixed into every subsequent message, binding the encrypted session to the specific handshake that created it.

## After the handshake: split

When the handshake finishes, `SymmetricState.split()` derives two independent `CipherStates` from the final chaining key:

- `fromInitiator` — used to encrypt messages sent by the Initiator, decrypted by the Responder.
- `fromResponder` — the other direction.

Two separate cipher states means the nonce counters are independent and the two sides can send simultaneously without coordinating. Each direction is keyed differently, so a message sent one way can't be replayed back the other.

## Patterns

The Noise spec defines a small grammar of handshake patterns. A pattern specifies:

- What each side already knows before the handshake starts (pre-shared knowledge).
- The sequence of messages exchanged.
- Which DH operations happen at each step.

trueseal-noise implements two of them:

- **XX** — no pre-shared knowledge, mutual authentication, three messages.
- **NK** — Initiator already knows the Responder's static key, Initiator stays anonymous, two messages.
