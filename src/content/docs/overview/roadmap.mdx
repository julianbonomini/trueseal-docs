# Roadmap & Research

TrueSeal is a Developer Preview. It delivers end-to-end encrypted messages between the devices of a group, through a relay that can't read or forge them. What 1.0 needs is a commitment. The research direction after it is only an intent, and I'd rather keep the two apart.

## Before 1.0

The preview ends when these four things are true, and not before. There is no target date.

1. Identity keys are stored in the Keychain on Apple platforms and the Keystore on Android, and Session State is encrypted at rest. Today both rely on file permissions and, where there is one, the app sandbox.
2. The SDK APIs follow semver, so a breaking change needs a new major version. A CI check of each SDK's API enforces it.
3. Stored data, on devices and on the relay, migrates forward within a major version, with no Store Reset.
4. Each major version speaks exactly one Transport Version and one End-to-End Version. A protocol change is a new major version.

## Not planned for 1.0

- **An external security audit.** None is planned. Each public claim names the tests that prove it, and "not independently audited" stays a listed limitation.
- **End-to-end forward secrecy.** Messages are sealed to each device's long-lived key, so someone who steals a device's key can read the messages to it that they recorded. A ratchet that fixes this is a candidate for 2.0, because it changes the protocol.
- **Hiding a device's IP address from the relay's host.** It can come later without a protocol change. Until then, a user who needs it can use a VPN or Tor.
- **A hosted relay.** Whether to run one is a business decision, and 1.0 doesn't wait for it. You run your own relay.
- **Rust crates on crates.io.** That needs a separate decision to keep the Rust API stable.

## Research direction

Today every member of a group receives every message. The direction I want to explore is a device receiving only the messages it holds a capability for.

The addressed encryption TrueSeal already uses points at how. A message is sealed to a public key, and only the holder of the private key can open it. If a message could be sealed to a key for one object or one topic instead of a device, holding that key would be the permission to read it, and no server would decide who gets what.

Sealing to such a key is the easy part. The open question is how a device gets a new key of that kind without a full pairing and without someone in the middle handing keys out, while the relay still learns nothing new. Pairing hands out keys for a whole device. I don't know yet how to do it per object or per topic, and I'm not promising that it will ship.
