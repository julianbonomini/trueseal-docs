# Inbox & TTL

The Inbox is the relay's storage unit. Every device has one — a set of blobs addressed to its public key that haven't been delivered yet. The relay's whole storage model is built around that one structure.

## The InboxStore contract

Four operations:

**Put** — store a blob for a recipient. The blob is persisted durably *before* the relay sends an Ack. A relay that crashes between Put and Ack leaves the sender uncertain, so the client's outbox replays it on reconnect. Put never deduplicates: if the same blob arrives twice, both copies are stored. Both copies carry the same Message ID, and the library drops a copy it has already handled.

**Flush** — fetch all blobs for a recipient without deleting them. Returns blobs in insertion order (FIFO). They stay in the store until a DeliverAck is received for each.

**Delete** — delete a specific blob by ID after a DeliverAck arrives. If the session drops before the ack lands, the blob survives and comes around again on the next Receive Session. Clients must handle duplicates.

**Reap** — delete all blobs whose TTL has elapsed. Called periodically by the reaper goroutine. Reaping is policy, not data loss — it's what stops abandoned and permanently offline devices from making storage grow without bound.

## SQLite backend

The default backend is SQLite. Schema:

```sql
CREATE TABLE inbox (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    recipient   BLOB    NOT NULL,  -- 32-byte X25519 public key
    envelope    BLOB    NOT NULL,  -- raw protobuf Envelope bytes
    expires_at  INTEGER NOT NULL   -- Unix timestamp
);
```

SQLite is opened in WAL mode with `synchronous=FULL`, so every Put is crash-safe before the Ack goes out. A single connection serialises all writes, which avoids `SQLITE_BUSY` under concurrency.

## TTL and reaping

Every blob has a TTL set at Put time. When it expires, the blob becomes eligible for reaping. The reaper runs on a configurable interval (default: 1 hour) and deletes all expired blobs in one sweep.

Default TTL is 30 days, deliberately generous. Reaping is a last resort for permanently offline or abandoned devices, not routine housekeeping. Operators with tighter storage budgets can shorten the TTL.

A device that reconnects after its blobs have already been reaped will miss them permanently. [Delivery issues](/docs/integrate/delivery-issues) lists what the devices are and aren't told.
