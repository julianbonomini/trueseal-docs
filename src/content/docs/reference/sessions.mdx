# Sessions

trueseal-relay handles two distinct session types. Each uses a different Noise handshake pattern and exists for a different reason. They run on separate TCP listeners.

## Push Sessions

A Push Session is short-lived and anonymous. A device opens one, drops off some blobs, closes it.

**Handshake:** Noise NK. The device verifies the relay's static public key (confirming it's talking to the real relay). A fresh ephemeral X25519 keypair is generated for each Push Session and thrown away the instant it's done. The handshake gives the relay no device key to link a Push Session to a device or a Receive Session. It can still often link them by IP address or timing.

**Flow:**
1. Device opens a TCP connection to the push listener (default `:7701`).
2. Noise NK handshake completes — relay authenticated, device anonymous.
3. Device sends one or more `Push` frames, one per recipient blob.
4. For each Push: relay persists the blob to the Inbox, sends `Ack`.
5. If a blob is rejected (say, oversized), the relay sends `Error` and the device must not retry it.
6. Device closes the connection when it's done.

Multiple blobs can ride a single Push Session. One Ack per blob, in order.

## Receive Sessions

A Receive Session is long-lived and authenticated. A device opens one and keeps it open so blobs arrive in real time.

**Handshake:** Noise XX. Mutual authentication — device and relay verify each other's static public keys. The relay learns the device's stable noise public key and marks it as online.

**Flow:**
1. Device opens a TCP connection to the receive listener (default `:7700`).
2. Noise XX handshake completes — both sides authenticated.
3. Relay flushes anything already in the device's Inbox — delivered without deletion yet.
4. Relay delivers new blobs as they arrive, immediately, no polling.
5. For each Deliver frame the client receives, it durably persists the blob, then sends a **DeliverAck** with the blob's ID.
6. The relay deletes the blob on receipt of DeliverAck. If the session drops before the ack arrives, the blob survives and gets re-delivered on the next Receive Session. Clients have to handle duplicates.
7. Either side sends `Heartbeat` on idle to keep NAT/firewall tables happy; the other side echoes it.
8. Session stays open until the device disconnects or the connection drops.

The relay expects one Receive Session per device at a time, but it allows concurrent sessions on the same key — that can briefly happen during reconnect. Atomic Inbox flushing makes sure only one session wins the flush race, so the same blob never goes out twice in parallel.

## Heartbeat

Idle TCP connections get silently killed by NAT tables and firewalls, usually somewhere in the 30–300 second window. trueseal-relay sends `Heartbeat` frames on idle Receive Sessions to keep them alive, and the client echoes one back. Either side can initiate.

The interval is configurable. If a device stops responding to heartbeats, the relay closes the connection and lets the device reconnect.
